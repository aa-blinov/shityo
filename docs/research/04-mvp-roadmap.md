# 04 — MVP-скоуп и роадмап пилота

**Цель.** Зафиксировать *реалистичный* объём MVP для команды 2–4 человек, который можно довести до рабочего пилота (2D-генерация → SVG/DXF/PDF → браузерное превью → базовый 3D-превью), и дать инженерный план: состав изделий, схема мерок, фазы с оценками, стратегия QA, журнал угроз и допущений.

**Дата проверки источников:** 2026-11-03. Все URL открыты лично в этой сессии.

**Три вещи, которые нужно решить до начала кода** (иначе MVP разъедется):

1. **Семантика номера размера.** Сейчас в дереве три разные сетки с разной логикой (§B.5) — это надо схлопнуть в одну, иначе «размер 42» в футболке и в юбке будет означать разное.
2. **Половинные мерки vs полные.** ГОСТ-таблицы типовых фигур в половине обхвата, а наш API — в полном. Смешение даст ×2 в ошибках (см. §B.4).
3. **Что означает `back_length`.** В дереве это *длина изделия* (72 см), а в ГОСТ 17521-72 признак 40 — *длина спины до талии* (≈45 см для мужчины 176/92). Переименовать, пока API-контракт не заморожен у пользователей.

# Часть A — Состав MVP: четыре изделия и их конструктивная зависимость

## A.1 Почему именно эти четыре

Ключ отбора — **конструктивная зависимость**: каждое следующее изделие должно быть дешевле предыдущего по числу новых геометрических примитивов, потому что примитивы уже проверены на простых изделиях. Порядок реализации — это порядок зависимостей, а не приоритет рынка.

| # | Изделие | id в API | Детали (piece id) | Новые примитивы относительно предыдущего | Зависит от |
|---|---|---|---|---|---|
| 1 | **Футболка универсальная** | `tee` | `front`, `back`, `sleeve` | базовая сетка, симметрия, кривая Безье, горловина, пройма, рукав, зерно, насечки | — (фундамент) |
| 2 | **Прямая юбка** | `skirt` | `skirt` | расклешение/flare, подол, fold-линия, кривая бокового шва | только мерки талии/бёдер (не зависит от футболки) |
| 3 | **Прямые брюки** | `trousers` | `front`, `back` | **глубина шага и кривая шага** (самое дорогое), разрезная штанина, вынос сгиба, две длины | мерки талии/бёдер/шага/шагового шва |
| 4 | **Простая рубашка** | `shirt` | `front`, `back`, `sleeve`, `collar` | **вытачки**, планка, стойка+отложной воротник, манжета | корпус футболки + воротник (зависит от №1) |

**Обоснование по зависимостям:**

- **Футболка — фундамент блока.** Не имеет вытачек, не имеет воротника, не имеет подкладки: три контура (перед/спинка/рукав) и четыре типа кривых (горловина, плечо, пройма, окат рукава). Любая ошибка в базовой сетке (симметрия, единицы, замыкание контура) проявится сразу и дёшево чинится.
- **Юбка — независимая ветка.** Не наследует ничего от футболки, кроме ядра геометрии. Одна деталь, кроится по сгибу → идеальна для проверки раскладки листов и экспорта. Дешёвый второй результат.
- **Брюки — самая дорогая геометрия в MVP.** Вводят кривую шага (crotch curve) и два независимых по длине отрезка (глубина шага + шаговый шов). Именно здесь чаще всего ошибаются в пропорциях, поэтому идёт третьим, когда ядро уже обкатано.
- **Рубашка — последняя.** Это футболка + 4 новых узла (вытачки, планка, воротник на стойке, манжета). Каждый новый узел — источник своей посадки; добавлять их до стабилизации рукава и корпуса — умножать отладку.

**Что сознательно НЕ входит в MVP** (и почему):

| Не входит | Причина | Когда вернём |
|---|---|---|
| Детские размеры | отдельные пропорции, +1 таблица и отдельная валидация | после пилота |
| Брюки-шлёпки, джинсы, юбки-карандаш | каждая — своя посадка (вынос сгиба, занижение талии) | по заявкам пилота |
| Подкладка, карманы, рельефы, застёжка на молнии | не влияют на посадку, только на раскрой | после пилота |
| Моделирование «поверх» размера (прибавки по параметрам) | сейчас есть грубые `ease_*`; полноценное — отдельный слой | Ф3+ |
| Ткань/симуляция в 3D | нужен солвер, браузерный бюджет, воспроизводимость | вне MVP (см. 03) |
| Градация размеров (grade rules) | размеры дискретные, это осознанное упрощение MVP | после пилота |
| Экспорт в форматы швейного цеха (DXF AAMA/ASTM строго, PDF-tiled по ГОСТ) | делаем базовый экспорт + проверку; полный conformance-тест — отдельная задача | Ф3 |

## A.2 Конструктивные точки по каждому изделию

Ниже — **полный перечень опорных точек и формул**, которые движок должен вычислить. Формулы, совпадающие с текущим кодом в дереве, помечены `[VERIFIED: backend/app/drafts/*.py]`; новые — `[PROPOSAL]`.

### A.2.1 Футболка (`tee`) — 3 детали

Базовые величины (все в сантиметрах, геометрия деталей хранится в мм):

| Обозначение | Формула | Комментарий |
|---|---|---|
| `panel_width` | `bust / 2 + ease_bust` | ширина одной панели (перед = спинка) `[VERIFIED: tee.py:43]` |
| `half_width` | `panel_width / 2` | половина панели — от центра переда до бокового шва `[VERIFIED: tee.py:44]` |
| `neck_half` | `neck_circumference / 4 + 0.5` | половина ширины горловины `[VERIFIED: tee.py:46]` |
| `shoulder_drop` | `4.5` (футболка) | наклон плечевого шва, см `[VERIFIED: tee.py:47]` |
| `armhole_depth` | `bust / 4 + 6` | глубина проймы от горловины; классическое правило русской методики «ОГ3/4 + 6…7 см» `[VERIFIED: tee.py:48]` + `[INFERRED]` происхождение правила |
| `shoulder_tip_x` | `half_width - 1.5` | плечевая точка, отступ от бокового шва `[VERIFIED: tee.py:49]` |
| `front_length` | `back_length + length_delta + ease_length` | длина переда с запасом `[VERIFIED: tee.py:51]` |
| `back_length` | `back_length + length_delta + ease_length` | длина спинки `[VERIFIED: tee.py:74]` |
| `neck_depth` | `crew 8.5 / v 20 / square 4 / scoop 11` | глубина горловины по типу `[VERIFIED: tee.py:14-18]` |
| `cap_half` (рукав) | `0.23 * bust` | половина ширины оката; ≈ обхват проймы/2 `[VERIFIED: tee.py:163]` |
| `cap_rise` | `6.5` | высота оката `[VERIFIED]` |
| `underarm_drop` | `4.0` | глубина подмышечной выемки `[VERIFIED]` |
| `hem_half` (рукав) | `cap_half - 4.0` | сужение к низу рукава `[VERIFIED]` |

Контурные точки детали (правая половина, затем зеркалится):
`O` — центр горловины (0,0) → `N` — край горловины (`neck_half`, 0) → `S` — плечевая точка (`shoulder_tip_x`, `shoulder_drop`) → `A` — нижняя точка проймы (`half_width`, `armhole_depth`) → `H` — низ бокового шва (`half_width`, length) → `O'` — центр низа (0, length).

Кривые (все — кубический Безье, `[VERIFIED: tee.py:107-137]`):
1. **Горловина** — контрольные точки `(0, neck_depth*0.85)`, `(neck_half*0.85, neck_depth)`.
2. **Плечевой шов** — `(neck_half + (tip-neck_half)*0.45, drop*0.25)`, `(tip-2.0, drop*0.8)`.
3. **Пройма** — `(tip, drop + (armhole_depth-drop)*0.55)`, `(half_width-1.0, armhole_depth-2.5)`.
4. **Окат рукава** — `(cap_half*0.35, -cap_rise*0.15)`, `(cap_half*0.72, cap_rise*0.55)`.

Служебная геометрия деталей: зерно — вертикаль по центру переда/спинки и по центру рукава; насачки — «пройма» (бок проймы), «бок» (низ бока), «подмышка», «низ» рукава; внутренние линии — «середина спинки» (fold) `[VERIFIED: tee.py:139-156]`.

### A.2.2 Юбка (`skirt`) — 1 деталь

| Обозначение | Формула | Комментарий |
|---|---|---|
| `waist_half` | `waist / 2 + ease_waist` | половина ширины пояса (деталь кроится вдвое, по сгибу) `[VERIFIED: skirt.py:31]` |
| `hip_half` | `hip / 2 + ease_hip` | половина ширины по бёдрам `[VERIFIED: skirt.py:32]` |
| `hem_half` | `hip_half + flare` | расклешение на сторону, см `[VERIFIED: skirt.py:33]` |
| `hip_y` | `min(total_length * 0.4, 20.0)` | линия бёдер, отсчёт от пояса `[VERIFIED: skirt.py:34]` |
| `total_length` | `skirt_length + length_delta` | длина изделия `[VERIFIED: skirt.py:30]` |

Точки: `O` (0,0) → `W` (`waist_half`, 0) → `Hp` (`hip_half`, `hip_y`) → `H` (`hem_half`, `total_length`) → `O'`. Кривые: боковой шов (Безье через 3 точки, промежуточная точка смещена к бедру) `[VERIFIED: skirt.py:41-46]`, подол (Безье с лёгким прогибом вниз, +0.8 см) `[VERIFIED: skirt.py:47-52]`. Служебное: fold-линия по центру, насачки «бок» и «сгиб», `cut = 2` `[VERIFIED]`.

### A.2.3 Брюки (`trousers`) — 2 детали

| Обозначение | Формула | Комментарий |
|---|---|---|
| `waist_width` | `waist / 4 + ease_waist` | ширина пояса **одной** штанины (в полном изделии 4 части: 2 перед + 2 зад) `[VERIFIED: trousers.py:35]` |
| `hip_width` | `hip / 4 + ease_hip` | ширина по бедру одной штанины `[VERIFIED: trousers.py:36]` |
| `total_length` | `crotch_depth + inseam_length + length_delta` | полная длина брюк `[VERIFIED: trousers.py:37]` |
| `knee_y` | `crotch_depth + knee_length` | линия колена `[VERIFIED]` |
| `hip_y` | `crotch_depth * 0.55` | линия бёдер `[VERIFIED]` |
| `front_extension` / `back_extension` | `3.5` / `7.0` | вынос переднего сгиба / за задний `[VERIFIED: trousers.py:41-42]` |
| задняя штанина | `waist + 1.5`, `hip + 3.0` | разница передов и зада сзади `[VERIFIED: trousers.py:57-58]` |
| `knee_width` | `(hip_width + waist_width) * 0.5 + 1.0` | `[VERIFIED: trousers.py:76]` |
| `hem_width` | `knee_width - 1.5` | сужение к низу `[VERIFIED: trousers.py:77]` |

Точки (передняя штанина): передний сгиб пояса `(-extension, 0)` → бок пояса `(waist_width, 0)` → бок на бёдрах `(hip_width, hip_y)` → бок на колене `(knee_width, knee_y)` → низ `(hem_width, total_length)` → внутренний шов `(0, total_length)` → **точка шага** `(0, crotch_depth)` → кривая шага обратно к переднему сгибу. Кривая шага — кубический Безье: `(0, crotch_depth - extension*0.9)`, `(-extension*0.75, crotch_depth*0.35)` `[VERIFIED: trousers.py:104-110]`. Служебное: зерно по длине штанины, насачки «бок»/«шаг»/«низ», fold-линия по сгибу, `cut = 2` `[VERIFIED]`.

### A.2.4 Рубашка (`shirt`) — 4 детали

| Обозначение | Формула | Комментарий |
|---|---|---|
| `panel_width`, `half_width`, `neck_half` | как у футболки | общий корпус `[VERIFIED: shirt.py:36-38]` |
| `shoulder_drop` | `5.0` | плечо рубашки круче, чем у футболки `[VERIFIED: shirt.py:39]` |

| вытачка переда | от бокового шва вверх, основание `(half_width-0.5, waist_y)`, остриё `(half_width-0.5, waist_y-dart_depth)` | `[VERIFIED: shirt.py:132-136]` |

> ### Важная поправка к формулировке задания
> В ТЗ упоминался **«ISO 7253-1»**. **Стандарта ISO 7253-1 не существует.** Номер 7253 у ISO занят другой темой: **ISO 7253:1996 «Paints and varnishes — Determination of resistance to neutral salt spray (fog)»** — лакокрасочные материалы; стандарт **отменён в 2006**, заменён на ISO 9227:2006 `[VERIFIED: https://www.iso.org/standard/20357.html]`. Для антропометрии одежды правильные номера — **ISO 7250-1** (определения и точки тела) и **ISO 8559-1** (определения мерок для размерной маркировки), плюс европейская серия **EN 13402-1/-2/-3**. Все ссылки в этом документе даны по проверенным номерам.

> ### Предупреждение 1: половина или полный обхват
> В ГОСТ-таблицах типовых фигур **горизонтальные обхваты торса приведены в половинном значении** (например, `Сш` = половина обхвата шеи, `Ст` = половина обхвата талии) `[VERIFIED: http://dmitriy-prog.ru/ru/points.html — «Мерки в горизонтальной плоскости торса измеряются в полном обхвате, а вводятся в половинном значении»]`. Наш API принимает и хранит **полные** обхваты. Любая таблица типовых фигур, перенесённая в наш движок, **обязана быть пересчитана ×2 для горизонтальных обхватов** — иначе получим фактор 2 в ошибке (см. риск R-04 в §D).

> ### Предупреждение 2: `shoulder_width` — две разные величины
> В ГОСТ есть **два разных признака**: №31 «Ширина плечевого ската» (от основания шеи до плечевой точки) и №53 «Плечевой диаметр» (между двумя плечевыми точками) `[VERIFIED: определения в ГОСТ 17521-72, табл. 2]`. Таблицы на emdi.ru и у dmitriy-prog.ru дают **первую** величину (15,7 у мужчины 176/RU48, 13,2 у женщины 164/RU42) `[VERIFIED]`, а наш API и фронт-3D используют **вторую** (46 в каталоге) `[VERIFIED: catalog.py]` — величину порядка 44–47 см для мужчины с обхватом груди 96 `[INFERRED: порядок величины из абсолютных значений ГОСТ 17521-72; в PDF-разметке таблицы строки разъехались, поэтому точное число брать из печатного оригинала]`. Это не ошибка, но при переносе таблиц легко перепутать: одно и то же слово «ширина плеча» означает разные вещи, различающиеся почти втрое. В UI подписать явно: «ширина плеч (плечевой диаметр)».

> ### Предупреждение 3: `back_length` — не признак ГОСТ
> ГОСТ 17521-72 №40 — «Длина спины до талии» ≈ **45 см** у мужчины 176/Ог3 92 `[VERIFIED: dmitriy-prog.ru, ГОСТ-методика]`. В нашем каталоге `back_length = 72` — это **длина изделия от горловины до низа** `[VERIFIED: tee.py:74, catalog.py]`. Значения расходятся в ~1.6 раза и означают разные вещи. **Решение:** переименовать в `body_length` (длина изделия) до заморозки контракта; если понадобится признак №40 — завести отдельное поле `back_length_to_waist`. `[PROPOSAL]`

> ### Предупреждение 4: часть мерок запрашивается, но не влияет на чертёж
> Сейчас `height` **не используется ни в одной** из четырёх конструкций; `shoulder_width` и `waist` запрашиваются футболкой и рубашкой, но в геометрию не входят (плечо считается от `bust` через `half_width`, талия влияет только на глубину вытачки рубашки через `fit`) `[VERIFIED: backend/app/drafts/{tee,shirt,trousers,skirt}.py — `require(...)` перечисляет мерку, но в формулах она не встречается]`. Для пользователя это выглядит как «мерка влияет на лекало», и любая ошибка в ней остаётся незамеченной. **Решение MVP:** либо включить мерки в геометрию (см. Ф2), либо убрать их из формы ввода и из `require()` — и явно написать, что изделие строится по обхвату груди/талии и длине. `[PROPOSAL]`

## B.4 Как размерная сетка отображается на мерки

### B.4.1 Первичное/вторичное измерение по типам изделий (EN 13402-2)

Таблица 1 EN 13402-2:2002 `[VERIFIED]` — выжимка по нашим четырём изделиям:

| Тип изделия | Мужчины: PD (SD) | Женщины: PD (SD) |
|---|---|---|
| Трикотаж, футболки | обхват груди (рост) | обхват груди (рост) |
| Рубашки | обхват шеи (рост, длина руки) | — |
| Брюки | обхват талии (рост, шаговый шов) | обхват талии (рост, обхват бёдер, шаговый шов) |
| Юбки | — | обхват талии (рост, обхват бёдер) |

**Практический вывод для MVP:** ровно одна *ведущая* мерка на изделие + одна–две *уточняющие*.
- `tee` / `shirt` → ведущая `bust`, уточняющая `height`.
- `trousers` → ведущая `waist`, уточняющие `height`, `inseam_length`.
- `skirt` → ведущая `waist`, уточняющие `height`, `hip`.

**Размерная сетка** = дискретный ряд (RU 42…48 для наших моделей), и в каждой строке — полный набор мерок фигуры этого размера (как сейчас в `backend/app/core/sizes.py`) `[VERIFIED: текущая реализация]`. Это соответствует модели EN 13402: маркировка — диапазон мер тела, а не «номер изделия». `[INFERRED]`

### B.4.2 Формат маркировки по EN 13402-3

- Числовой размер по EN 13402-3 §5.3.2 = **первичное измерение / рост / вторичное**, через слэш, в сантиметрах; например, футболка: `96/176`; диапазоны считаются как ±½ интервала `[VERIFIED: DIN EN 13402-3:2017, п. 4.3 и 5.3.2]`.
- Буквенный код: XXS…3XL (перечень в EN 13402-3:2017, п. 5.3.1); числовые диапазоны — в Приложении A, п. A.2.5: мужчины M = обхват груди 94–102, женщины M = обхват груди 90–98 `[VERIFIED: DIN EN 13402-3:2017 п. 5.3.1 + диапазоны, воспроизведённые в https://en.wikipedia.org/wiki/Joint_European_standard_for_size_labelling_of_clothes]`.
- Пиктограмма EN 13402-1 показывает, какие именно измерения использованы `[VERIFIED]`.

**Рекомендация для MVP:** показывать пользователю строку `RU 48 · 96–98 / 172–180 · M` — это и есть требуемая EN-маркировка, плюс привычный номер RU. `[PROPOSAL]`

### B.4.3 Соответствие RU ↔ EU ↔ US ↔ буквы

Рыночные таблицы соответствия (не стандарт!):

| RU (жен.) | EU | US | Международный | Обхват груди, см |
|---|---|---|---|---|
| 40 | 34 | 8 | XXS | 78–81 |
| 42 | 36 | 10 | XS | 82–86 |
| 44 | 38 | 12 | S | 86–89 |
| 46 | 40 | 14 | M | 90–93 |
| 48 | 42 | 16 | L | 94–97 |

`[VERIFIED: https://furtek.ru/tablitsy-sootnoshenija-razmerov-i-abbreviatury-na-jarlykax]`

Мужчины: европейский = российский номер; «M» = RU 48–50, рост 176, обхват груди 94–100 `[VERIFIED: там же]`.

> **Осторожно с «EU-номером».** EN 13402-3 **не определяет** числовых «EU-размеров» в нашем смысле — он оперирует мерками тела и интервалами `[VERIFIED]`. Старые ISO 3636/3637/4415/4416/4417/5971/7070, из которых бралась привычная EU-нумерация, **все отменены** `[VERIFIED: ISO/TC 133 catalogue]`. Рыночные соответствия выше — **конвенция продавцов**, а не нормативная таблица; при расхождении с EN-интервалами приоритет у EN. `[PROPOSAL]`

### B.4.4 EU 38–46 (запрошенный диапазон) → тело

Через EN 13402-3:2017, Таблица A.6/A.7 (женщины, размеры платья) `[VERIFIED]` — берём **средние значения** (mean value) и «диапазоны»:

| Обхват груди (среднее) | Диапазон | Обхват талии (среднее) | Диапазон | Обхват бёдер (среднее) | Диапазон |
|---|---|---|---|---|---|
| 84 | 82–86 | 68 | 66–70 | 92 | 90–94 |
| 88 | 86–90 | 72 | 70–74 | 96 | 94–98 |
| 92 | 90–94 | 76 | 74–78 | 100 | 98–102 |
| 96 | 94–98 | 80 | 78–82 | 104 | 102–106 |
| 100 | 98–102 | 84 | 82–86 | 108 | 106–110 |

Интервалы: обхват груди 4 см (≥104 — 6 см), талия 4 см (≥88 — 6 см), бёдра 4 см (≥112 — 5 см) `[VERIFIED: DIN EN 13402-3:2017, п. 4.1.2]`.

**Как это соотносится с RU:** обхват груди 84 → RU 42 (жен.), 88 → RU 44, 92 → RU 46, 96 → RU 48, 100 → RU 50. То есть **RU-номер = обхват груди / 2**, и «EU 38–46» по рыночной конвенции (RU − 6) покрывает обхват груди 84–100, т.е. **RU 42–50** `[INFERRED]`.

Итоговая таблица «размер → мерки», которую держит движок:

| RU | Обхват груди | Обхват талии | Обхват бёдер | Обхват шеи | Рост (муж.) | Рост (жен.) | EN-диапазон груди | EN-буква (жен.) |
|---|---|---|---|---|---|---|---|---|
| 42 | 84 | 63,5 | 90 | ~34,6 | — | 164 | 82–86 | S |
| 44 | 88 | 67,5 | 94 | ~35,6 | — | 170 | 86–90 | S/M |
| 46 | 92 | 71,5 | 98 | ~36,6 | 173 | — | 90–94 | M |
| 48 | 96 | 86 (муж.) | 100,5 (муж.) | 40,5 (муж.) | 176 | — | 94–98 | M/L |
| 50 | 100 | 90 (муж.) | 103,5 (муж.) | 41,5 (муж.) | 179 | — | 98–102 | L |

Значения мужской колонки — из emdi.ru, женской — из emdi.ru; шея/бёдра женщин для RU 42 — из ГОСТ-сетки (164/84/92) `[VERIFIED]`; соответствие EN-диапазонов — из EN 13402-3 `[VERIFIED]`; приведённое сопоставление RU↔EN — `[INFERRED]`.

## B.5 Размерные сетки, которые уже есть в дереве (и что с ними делать)

Текущий `backend/app/core/sizes.py` `[VERIFIED]` содержит четыре сетки, и они **не согласованы между собой**:

| Модель | «42» → мерки | Комментарий |
|---|---|---|
| `tee` | bust **88**, waist 76, height 170 | Обхват груди 88 = RU **44** по правилу «размер = Ог3/2» `[INFERRED]`; то есть номер **сдвинут на 2** |
| `shirt` | bust **92**, waist 80, height 170 | та же проблема: 92 = RU 46 |
| `trousers` | waist 74, hip 90, height 170 | согласуется с emdi (RU 42: талия 74) `[VERIFIED]` |
| `skirt` | waist 64, hip 88, height 168 | близко к RU 42 жен. (63,5 / 90), но не совпадает |

**Решение MVP `[PROPOSAL]`:**
1. Ввести **один** модуль `core/sizes.py` с **одной** сеткой фигур по ГОСТ-нумерации (рост × обхват груди × полнота), из которой **выводятся** все сетки моделей.
2. Номер размера = обхват груди / 2 (единообразно для обоих полов) `[VERIFIED]` по emdi.ru.
3. Размерные сетки моделей получать из общей сетки **проекцией**: для `trousers`/`skirt` ведущая мерка — талия, поэтому при равном номере размера берём ту фигуру, у которой талия совпадает с целевой; при отсутствии — интерполируем по полуинтервалу ГОСТ (4 см по Ог3, 4 см по От) `[VERIFIED: ГОСТ 31399-2009, п. 5.1]`.
4. До Ф1 считать текущие сетки **некорректными** и не показывать их пользователю как «ГОСТ-совместимые» (или явно подписать «ориентировочные значения»).

Цель: ловить ошибки ядра, а не «сравнивать картинки». Сейчас **89 юнит-тестов** в пяти файлах (`test_geometry` 10, `test_drafts` 17, `test_export` 27, `test_validation` 25, `test_api` 10) `[VERIFIED]` — ядро, конструкции, экспорт, валидатор и API уже покрыты; ниже — что **добить**:

| Группа | Что проверяем | Критерий |
|---|---|---|
| Точка/вектор | арифметика, `length()`, дистанции | точное равенство (float) |
| Безье | `at(0)=start`, `at(1)=end`, длина между хордой и контрольным многоугольником | `chord < length < polygon` (уже есть `[VERIFIED]`) |
| Флэттening | отклонение аппроксимации от кривой ≤ tolerance | ≤ tolerance (уже есть) |
| Замыкание контура | первая ≈ последняя точка | ≤ 0,5 мм (константа `CLOSURE_TOLERANCE_MM` из `core/validation.py` `[VERIFIED]`) |
| Площадь | знак и положительность для невырожденного контура | `area > 0` |
| Смещение контура | прибавка 10 мм увеличивает площадь и периметр, не инвертирует | `area(SA=10) > area(SA=0)` |
| Единицы | черчение в см → деталь в мм | ровно ×10 (конверсия на границе API) |
| Симметрия | зеркальная половина даёт симметричный замкнутый контур | max |x(левый)| == max |x(правый)| |

### C.3.2 Уровень 2 — golden/snapshot-тесты конструкций

Цель: ловить **незаметное** изменение формы (сдвиг точки на 2 мм не ломает юнит-тест, но меняет посадку).

- Эталон: JSON с **округлёнными до 0,1 мм** координатами контура каждой детали для фиксированного набора (модель × размер × набор параметров). Хранить в `backend/tests/golden/`.
- Сравнение: покоординатное с допуском **0,2 мм**; при превышении — печать diff-картинки (SVG) в отчёте pytest.
- Кейсы: 4 модели × 2 размера × 2 набора параметров (min/max прибавки) = **16 эталонов**; плюс 4 «негативных» (пустая мерка → ошибка, не эталон).
- Важно: golden-файлы **версионируются**; изменение эталона = изменение изделия, а не «тест сломался» — ревью обязательно.

### C.3.3 Уровень 3 — property-based тесты (hypothesis)

`hypothesis` 6.170.14 уже стоит в .venv, но не используется `[VERIFIED]`. Свойства, которые обязаны выполняться **для всех** допустимых мерок:

| Свойство | Формулировка |
|---|---|
| P1 Замыкание | контур любой детали замкнут (первая ≈ последняя точка, ≤ 0,5 мм) |
| P2 Положительность площади | `area > 0` и `area` конечна (не NaN/inf) |
| P3 Монотонность по обхвату | рост `bust` на 4 см ⇒ ширина переда растёт (с допуском 0) |
| P4 Монотонность по длине | рост `body_length` ⇒ высота детали не убывает |
| P5 Симметрия | деталь, построенная симметрично, симметрична: `max|x| слева == max|x| справа` |
| P6 Отсутствие вырожденности | bbox каждой детали > 0 по обеим осям |
| P7 Зерно внутри | оба конца линии зерна лежат в bbox детали |
| P8 Детерминированность | два вызова с одними и теми же мерками дают **побайтово** одинаковый JSON |
| P9 Диапазоны | любая мерка вне диапазона из справочника → `DraftError`/ошибка валидатора, а не «лекало вслепую» |
| P10 Прибавка не ломает геометрию | `ease ∈ [0, 40]` ⇒ P1–P7 выполняются |

Стратегии: `st.floats(min_value=..., max_value=..., allow_nan=False)` по каждой мерке из справочника; комбинации — `st.lists(...)` длиной 12 или `st.fixed_dictionaries`; `max_examples=200` на CI, `1000` локально; `deadline=None` для тяжёлых построений.

## C.4 Definition of Done пилота

Пилот считается готовым, если одновременно:

1. Все 4 модели строятся по **любой** допустимой мерке из справочника без ошибок; на недопустимой — понятная ошибка, а не «лекало вслепую».
2. Экспорт SVG/DXF/PDF печатается **1:1 мм** и проходит проверку двумя сторонними инструментами (§C.3.4 E9–E11).
3. Размерная сетка согласована с ГОСТ-нумерацией и показывает EN-диапазоны (§B.4.2).
4. Зелёные уровни QA 1–4 в CI.
5. ≥3 отшитых изделия (разные модели) с зафиксированными отклонениями посадки и выводами.
6. Лицензионно чисто: в зависимостях нет `pymupdf`/AGPL-пакетов (PDF — на BSD-`reportlab`); лекала — собственные формулы, не копия чужих данных (см. 01).
7. Документ «как мерить и шить» опубликован.
