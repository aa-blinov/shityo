## 1. Executive summary

**Что сделано.** Рабочий сервис: мерки и параметры фасона на входе ->
параметрически построенные лекала на выходе -> печать 1:1 в SVG, DXF и
PDF. Четыре типа изделий (футболка, рубашка, брюки, юбка), 2D-просмотр в
браузере, размерные сетки, проверка геометрии перед выдачей.

**Проверено фактами, а не обещаниями:**

- 94 теста Python зелёные (`pytest backend/tests`), 2 браузерных сценария
  Playwright зелёные (`npx playwright test` в `e2e/`).
- Экспорт проверен содержимым, а не только тестом: PDF открывается
  (`pypdf`), MediaBox A4 landscape = 841.89 x 595.28 pt, русские подписи
  извлекаются как «Перед - cut 1»; DXF читается обратно `ezdxf` и содержит
  слои CUT/SEAM/GRAINLINE/NOTCH/LABEL в миллиметрах; SVG - валидный XML в
  миллиметрах.
- Детерминизм: один и тот же вход даёт побайтово одинаковые координаты
  (тест `test_generation_is_deterministic`).

**Главный вывод исследования.** Собрать библиотеку базовых лекал из
открытых источников **можно на 60-70 % ассортимента, но не целиком и не
без лицензионной работы** ([research/01]). Причина не в нехватке чертежей:
её не хватает там, где нужна градация, детские блоки и женская
мультиразмерная таблица - там открытых решений нет вообще. Практический
путь - **портировать формулы** из permissive-проектов в собственный
движок, а не встраивать чужие рантаймы.

**Лицензия - главный риск, и он закрыт до релиза.** В процессе работы
выяснилось, что первая версия экспорта PDF использовала PyMuPDF (AGPL-3.0 с
сетевым триггером). Для коммерческого SaaS это блокер, поэтому экспорт
переведён на reportlab (BSD-3-Clause), а пакеты `pymupdf*` удалены из
окружения. Шрифт с кириллицей (DejaVu Sans, лицензия Bitstream Vera)
вендорен в репозиторий, чтобы подписи печатались одинаково на Windows,
Linux и CI.

**Реалистичный путь.** Не «своё CAD из всего сразу», а: пилота с
детерминированным движком на четыре изделия (сделано) -> перенос
конструкций в декларативный формат, чтобы модель правил конструктор без
программиста (следующий этап) -> импорт внешних лекал как спецификаций ->
3D-сборка деталей по швам и симуляция ткани (позже, с честной оговоркой,
что браузерная физика ткани - не промышленная).

**Чего продукт не делает.** Не делает примерку: 3D-превью - геометрическая
иллюстрация положения деталей на параметрическом манекене, и это подписано
в интерфейсе. Не проверяет посадку на человеке: зелёные проверки означают
«геометрия корректна и детали сопрягаются», а не «сядет идеально».

## 1a. Дефекты, найденные и исправленные при приёмке пилота

Их стоит назвать, потому что они показывают, что проверка была не
формальной.

| Дефект | Как обнаружен | Исправление |
|---|---|---|
| **Крой не сходился по обхватам**: футболка 104 см вместо 100, брюки 128 вместо 90, юбка 248 вместо 76 | сверка суммы ширин деталей с обхватом | Единое правило раскладки: ширина детали от центра до бокового шва = (обхват + прибавка) / 4. Каждая деталь сообщает свою долю обхвата, сумма проверяется тестом |
| **Рукав шире руки на 12 см**: ширина оката подгонялась под длину проймы | сверка с MIT-эталоном FreeSewing (26 точек построения) | Ширина рукава - из обхвата бицепса, длина оката - из длины проймы. Это два независимых ограничения |
| **Вырез горловины физически невозможен**: 230 мм при шее 360 мм | та же сверка | Горловина подбирается итеративно: длина выреза переда и спинки равна обхвату шеи с прибавкой. Сходится с точностью 0.3 мм |
| **Глубина проймы не зависела от фигуры**: считалась как bust/4 + 6 | та же сверка | Из вертикальных мерок: «от шеи до талии» минус «от талии до подмышки» |
| **Вытачка рубашки была константой** по посадке | та же сверка | Считается из разности обхватов груди и талии: на полной фигуре вытачка глубже, на худой - лишняя |
| **Низ изделия игнорировал обхват бёдер** | та же сверка | Низ держит обхват бёдер: изделие расширяется книзу, если бёдра шире груди |
| Окат рукава не совпадал с проймой | та же сверка | Длина оката подбирается делением отрезка под сумму длин пройм переда и спинки; проверяется тестом по подписанным швам |
| Горловина строилась двумя ямами вместо одной | визуальный контроль чертежа | Половина детали начинается от середины выреза, зеркалирование даёт одну общую горловину |
| Брюки строились по неверной раскладке: сгиб и передний сгиб разнесены, кривой шага нет | визуальный контроль | Классическая раскладка половинки штанины: боковой шов слева, передний сгиб справа, кривая шага между ними |
| Воротник рубашки был замкнутым овалом | визуальный контроль | Половина воротника: сгиб слева, линия притачивания сверху, внешний край снизу |
| `height`, `shoulder_width`, `waist` запрашивались, но не влияли на чертёж | сквозной тест «каждая мерка меняет чертёж» | Рост исключён из числа мерок кроя (все вертикали берутся из своих мерок); ширина плеча задаёт положение плечевой точки, талия - сужение бокового шва |
| Припуск на швы выходил за границы вида, детали срезались по краю окна | измерение экранных координат деталей | Припуск добавлен в границы вида |
| Размерная сетка не применялась: клик по строке ничего не делал | прогон в браузере | Применение по кнопке «Применить» в строке; проверяется, что ширина детали изменилась |
| Заголовки таблицы и деталей были сырыми ключами (`bust`, `front`) | скриншот | Подписи из словаря: «Обхват груди», «Перед» |
| Таблица размеров не помещалась в панель | скриншот | Показаны опорные мерки и ширина переда, подписи сокращены |
| Холст рос под содержимое лекал вместо того, чтобы вписывать его в окно | измерение размеров в браузере | `grid-template-rows: minmax(0, 1fr)` и `overflow: hidden` |
| SSR показывал фикстуры вместо данных бэкенда, плюс плашка «офлайн-данные» | скриншот рабочей области | Прямой адрес бэкенда на сервере; `store.source = data.source` |
| 3D-превью было пустым: сцена в сантиметрах, камера в метрах | скриншот 3D | Манекен и панели переведены в метры |
| Экспорт отдавался как JSON вместо файла | проверка ответа API | `Response(content=..., media_type=...)` для SVG, DXF, PDF |
| PDF печатал русские подписи квадратами (Helvetica без кириллицы) | извлечение текста из PDF | DejaVu Sans вендорен в репозиторий, транслитерация как последний fallback |

## 3. Лицензионный анализ

Полный анализ - `docs/research/01` (разделы 3-4). Правила, которые
применяются в продукте:

1. **Код и данные лицензируются раздельно.** Если лицензия данных не
   объявлена отдельно, данные молча наследуют GPL репозитория. Для
   Seamly2D, Valentina, TMTP, OpenPattern это означает: читать как
   спецификацию, не распространять файлы.
2. **CC BY - безопасно** (атрибуция). **CC BY-SA - share-alike на
   производных**: наш производный файл обязан остаться CC BY-SA
   (проверено по legalcode §3(b)(1)), поэтому файлы под BY-SA изолируются
   в отдельной зоне или не берутся.
3. **Разделение репозитория:** `LICENSE-CODE.md` (наш код) и
   `LICENSE-DATA.md` + NOTICE (импортированные лекала). Это и юридическая
   гигиена, и продуктовая фича «на чём основана эта выкройка».
4. **Реестр происхождения** для каждого блока: `source_project`,
   `source_author`, `source_license`, `source_url`, `modifications`.
5. **Не линковать GPL/AGPL-движки.** Сверка - отдельным headless-контейнером
   на этапе разработки, результат - числа, не артефакты.
6. **PyMuPDF закрыт до релиза:** AGPL -> reportlab (ADR-009).
7. **franken_textiles** имеет rider, запрещающий предоставление ПО
   производным работам OpenAI/Anthropic - при наличии внешнего LLM-слой
   надо перечитать rider дословно.

## 4. Математические основы

Полный разбор - `docs/research/02-math-and-libraries.md` (1679 строк).

**Метод.** Опорные точки по антропометрическим формулам, кривые - кубические
Безье, зависимости - направленный ациклический граф, формулы - в
песочнице без `eval`.

**Антропометрическая базовая сетка** (формулы ЦОТШЛ/СКФУ, проверены по
источнику): `РП = Сг/4 + Вп + Пк/3 + Пс.пр`, `А₀Г = ВпрзII + Пспр + 0,5 Пдтс`,
`Г₁П₃ = 0,5 П₂Г₁ + 1,5`.

**Примитивы построения** - 11 штук, таксономия взята из документации
Seamly2D: базовая сетка, точки, линии, дуги, кривые, вытачки, припуски,
параллельные и перпендикулярные линии, симметрия, перенос точки.

**Площадь кривой - по формуле Гирилла (точная), длина - адаптивной
аппроксимацией с допуском.**

**Вытачки:** перенос точки - пересечение окружностей; глубина задаётся
параметром.

**Пройма и окат:** численный метод (категории Low/Average/High, ease 1"),
apex подбирается итеративно.

**Градация:** три метода (линейный, мультипликативный, смешанный) плюс
**таблица приращений ЕМКО СЭВ П.4.1**, проверенная построчно по исходному
PDF.

**26 проверок** V-01...V-26 по шести группам: геометрическая
непротиворечивость, самопересечения, сопряжение деталей, длины швов,
диапазоны мерок, припуски и углы, стабильность на крайних размерах.

**Подход A против B.** A (перестроение по формулам) - основа проекта:
ошибки не накапливаются, потому что каждый расчёт выводится из мерок заново.
B (деформация шаблона) применяется точечно: там, где нужна ручная правка
формы, которую не описать формулой (произвольная вытачка, фигурный вырез).
Гибрид: **движок хранит конструкцию, а не картинку**; результат всегда
пересобирается из мерок, поэтому редактирование не накапливает ошибок.

**Библиотеки.** `shapely 2.2.0` (BSD-3) - только для предикатов в
валидаторе: сам Shapely признаёт, что не реализует гладкие кривые.
`ezdxf 1.4.5` (MIT) - экспорт. `reportlab 5.1.0` (BSD-3) - экспорт PDF.
`svgwrite 1.4.3` (MIT, maintenance mode). `numpy 2.5.4`, `scipy 1.18.1`
(BSD-3). `pypdf 6.21.4` (BSD) - чтение PDF в тестах.

**Rust/WASM отклонён с измеренным триггером пересмотра:** перестроение
детали - **0,33 мс**, `is_valid` - 1 мкс, `buffer` - 17 мкс. Узкое место
здесь не появится.

**Две ложные предпосылки исходного задания доказаны отрицательно:**
«система пропорциональных измерений» не является именованным методом, а
«правило трёх» как правило приращений не верифицируется - существует только
«правило трёх сигм».

| Слой | Выбор | Почему | Лицензия |
|---|---|---|---|

| Backend | **Python + FastAPI** | правила конструирования - это арифметика и кривые; библиотеки для этого на Python; один процесс вместо микросервисов | MIT |
| DXF | `ezdxf` | AAMA/ASTM-слои, миллиметры | MIT |
| PDF | `reportlab` | 1:1 мм, встраивание TTF с кириллицей | BSD-3 |
| Frontend | **SvelteKit 2 + Svelte 5 + TypeScript** | как в задании; состояние на рунах | MIT |
| 2D-слой | **собственный SVG** | печать 1:1 требует вектора; Konva SVG не экспортирует (открытый issue), Fabric дублирует геометрию | наш код |

**Про браузерную физику ткани - честно.** Rapier получил soft bodies
(0.21.0), «ткань 20x20 частиц на манекене» реалистична. Но точная драпировка
с самоконтактом - нереалистична в браузере. Поэтому 3D-физика - этап 3, и
в пилоте её нет.

## 7. Архитектура

Диаграммы - в `docs/ARCHITECTURE.md`. Ключевые решения:

- **Один процесс FastAPI.** Маршруты, каталог, генерация, экспорт,
  валидация. Микросервисы - преждевременное усложнение: критический путь
  не должен пересекать сетевые границы (ADR-004).
- **Фронтенд не считает геометрию.** Он получает готовые полигоны в
  миллиметрах. Иначе расхождение между картинкой на экране и содержимым
  PDF - вопрос времени.
- **Границы модулей** (`app/core/geometry.py`, `app/drafts/*`,
  `app/core/validation.py`, `app/export/*`, `app/api/*`) зафиксированы в
  ADR и проверяются тестами на границах.

## 8. Внутренняя модель лекал

Формат - `docs/FORMAT.md`. Ключевое: модель хранит **конструкцию** (мерки,
диапазоны, формулы, точки, кривые, правила фасона), а не готовую выкройку.
Выкройка получается детерминированным применением правил.

Схема модели - JSON с обязательным `format_version`, списком мерок с
диапазонами, параметрами фасона, именованными точками, кривыми, деталями,
связями между деталями, швами и припусками, технологическими метками,
происхождением и лицензией.

**Формулы исполняются в песочнице:** AST вместо `eval`, белый список
функций, проверка имён и глубины выражения.

**Статус:** в пилоте конструкции заданы кодом (`backend/app/drafts/*.py`),
декларативный формат - цель следующего этапа. Каталог уже отдаётся в том
же JSON, что и формат.

## 9. Алгоритм генерации

```
мерки + параметры фасона
  -> build_draft(model, measurements, params)      # app/drafts/*
     -> require(...)                               # проверка наличия мерок
     -> опорные точки по формулам                  # сантиметры
     -> кривые Безье по контрольным точкам
     -> to_mm(...)                                 # деталь в миллиметрах
     -> Piece(outline, notches, grainline, internal_lines)
  -> validate(pieces, measurements, params)        # app/core/validation.py
     -> замкнутость, простота, площадь, припуск, зерно, диапазоны
  -> ответ API: {pieces, warnings, errors, metrics}
```

Ключевое свойство: **результат пересобирается заново**, а не
модифицируется. Поэтому правка мерки не может оставить деталь в
противоречивом состоянии - она его пересчитает.

## 11. 2D/3D

**2D - сделано.** SVG-холст: панорама, зум, выбор детали, слои (линия
шва, припуск, зерно, надсечки, вытачки), список деталей с габаритами и
площадью, панель мерок и параметров, размерная сетка, экспорт.

**Интерфейс - на ките `@monos/ui`** (Apache-2.0, 70 компонентов, шесть
палитр, светлая и тёмная). Приложение не рисует ничего само: палитра,
радиусы, шрифт и фокусное кольцо - токены кита, страница переключает их
атрибутами `data-theme` и `data-mode`. Кита собрана на Svelte 4, а
приложение на Svelte 5, поэтому её компоненты компилируются в
legacy-режиме и работают без изменений.

Что дал переход на кит:

- единый визуальный язык вместо самописных CSS-правил, разъезжавшихся
  между экранами;
- доступные по умолчанию контролы: фокусное кольцо, ловушка фокуса в
  модальных окнах, `aria` на полях;
- темы из коробки: шесть палитр и переключатель светлого и тёмного режима.

**Локализация - словари, а не строки в шаблонах.** Русский и английский
живут в `frontend/src/lib/i18n/`, ключи плоские и сгруппированы по
экранам. Язык - стор: компонент читает `$t('ключ')` и перерисовывается сам
при смене языка. Переключатель в шапке, выбор сохраняется в localStorage.

Замечания валидатора приходят с сервера **кодами**, а не текстом:
`{code, params, text}`. Текст по умолчанию на русском лежит в
`backend/app/core/issues.py`, фронтенд строит по коду перевод на языке
интерфейса. Это убрало смесь языков в английском режиме.

Проверка `npm run check:i18n` сверяет: набор ключей двух словарей, наличие
перевода каждого кода замечания, совпадение плейсхолдеров с шаблоном из
бэкенда и отсутствие переводов несуществующих кодов.

**3D - физика ткани на готовом движке Rapier** (Apache-2.0, версия 0.21 с
soft bodies). Это не самописная физика: Rapier считает поведение мягких
тел, нам остаётся построить сетку и сшить детали.

Как это устроено:

1. Контур каждой детали триангулируется (отсечение ушей) и делится на
   треугольники.
2. Ткань **двусторонняя**: две копии сетки, разведённые на 5 мм по
   нормали. Односторонняя плоская сетка вырождается - тело проваливается на
   десятки метров.
3. Ячейки - тетраэдры по четыре индекса: Rapier группирует тройки-треугольники
   как попало.
4. **Всё изделие - одно мягкое тело.** Детали добавляются в него через
   `SoftBodyDesc.append`, швы сшиваются добавлением рёбер между частицами
   разных деталей. Проверено экспериментом: раздельные тела со стяжками
   расходятся на 15 см за несколько секунд, одно тело со сшитыми рёбрами
   держит шов с точностью до долей миллиметра.
5. Перед разворачивается по поверхности торса, спинка - по задней половине,
   рукав - вдоль руки. Плоскую деталь нельзя просто поставить вертикально:
   она упадёт полоской.
6. Плечевой шов закреплён - ткань висит на плечах и провисает под
   гравитацией.

**Честно о пределах.** Это геометрическая драпировка по сетке, а не
промышленная примерка: точность зависит от разрешения сетки и от того,
насколько точно совпали швы. Посадку по фигуре она не гарантирует - это
подписано прямо в интерфейсе. Решающий солвер Rapier
(`SoftBodySolver.Fem`) в этой задаче непригоден: 40 мс на шаг при 242
ячейках вместо нужных десятков, поэтому используется решатель по
ограничениям.

## 12. Контроль качества

`docs/QUALITY.md`. Пять уровней: юнит геометрии, юнит конструкций,
API-тесты, проверки локализации, браузерные сценарии. Плюс property-based
проверки, которые должны появиться на этапе расширения (предельные мерки по
всем моделям, монотонность параметров, припуск всегда наружу).

Проверки локализации (`frontend/scripts/check-i18n.mjs`) - не отдельный
язык, а сверка словарей с бэкендом: одинаковый набор ключей, перевод
каждого кода замечания, совпадение плейсхолдеров с шаблоном из
`backend/app/core/issues.py`.

**Что нельзя проверить автоматически** - перечислено прямо: посадка на
фигуре, технологическая пригодность, баланс изделия, удобство раскроя.
Зелёный статус означает «лекало геометрически корректно, параметры в
допустимых диапазонах, детали сопрягаются по длине» - и не больше.

## Итоговая рекомендация

**Какие проекты использовать.** FreeSewing, GarmentCode/pygarment, Moldeon,
ChristinaHein/shirt - как **спецификации формул**, которые портируются в
наш движок. Seamly2D, Valentina, TMTP, OpenPattern - как справочный
материал по методике, без копирования файлов. MakeHuman/MPFB2 - как CC0-ассеты
для 3D.

**Откуда брать базовые модели.** Своими силами, начиная с тех четырёх
моделей, что уже реализованы. Портированные формулы - ускорение, а не
основа: собственная библиотека нужна в любом случае, потому что
градации, детских блоков и женской мультиразмерной таблицы нет ни у кого.

**Что переиспользовать без переписывания.** Форматы обмена
(AAMA/ASTM-DXF, SVG, PDF 1:1), идею градации по именованным точкам,
структуру разделения «движок - конструкции - валидация - экспорт»,
накопленные методические формулы.

**Что разрабатывать самим.** Движок, конструкции, градацию, редактор
моделей, импорт, 3D-сборку и физику.

**Как организовать импорт.** Формат `docs/FORMAT.md` как единая точка входа:
конвертер читает чужой формат и пишет нашу модель; параметризация при
этом либо восстанавливается, либо помечается `parametrization: "static"` -
и тогда она не выдаётся за параметрическую конструкцию.

**Какой стек.** Python/FastAPI + собственное геометрическое ядро;
SvelteKit 5/TypeScript + собственный SVG-слой; three.js для 3D;
ezdxf + reportlab для экспорта. Rust/WASM - отклонён до появления
измеримого узкого места.

**С какой модели начать.** Футболка - она уже сделана и покрывает базовую
сетку, симметрию, кривые, горловину, пройму, рукав, зерно и надсечки.

**Какие гипотезы проверять первыми.** (1) Порт формул FreeSewing в наш
движок: сколько реально займёт один блок. (2) Качество построения по
внешней оценке конструктора. (3) Нужен ли собственный градационный движок
или дешевле купить. (4) Реалистичность 3D-примера на браузерной физике.
